Archive Tier Sunset
Situation

OCI Object Storage was deprecating Archive Tier to simplify the storage model from three tiers to two — Standard and Infrequent Access — while maintaining customer experience, storage semantics, and billing correctness. The migration required moving Archive-tier buckets to Standard and Archive-tier objects to Infrequent Access, preventing new Archive usage, and subsequently removing Archive Tier from storage workflows and customer-facing interfaces.

Action

Led the design and implementation strategy for the Archive Tier sunset across the Object Storage stack, including:

  • Bucket creation and storage-tier behavior
  • Object upload and storage-tier updates
  • Object Lifecycle Management (OLM) policy evaluation and transitions
  • Auto-Tiering behavior and customer cost optimization
  • Metadata API behavior and storage-tier representation
  • Metering, billing, retention, restore, GET/LIST, and PUT/DELETE semantics
  • REST API, CLI, and Console behavior
  • Storage capacity metrics integration with Horizon for capacity forecasting and planning

The Archive Tier sunset was executed through two parallel workstreams:

Phase 1: Transparently expose existing Archive buckets as Standard and Archive objects as Infrequent Access, block creation of new Archive resources, update OLM transitions, remove Archive from storage-tier enums and API responses, and preserve backward-compatible customer behavior during the transition.

Phase 2: Migrate all Archive-tier objects to Infrequent Access, complete the required metadata migration/backfill, and fully remove Archive-tier object support from storage workflows and customer-facing surfaces.

Complexity

Drove a cross-surface storage-tier deprecation spanning public APIs, CLI/Console UX, OLM policy semantics, metadata consistency, metering and retention behavior, MDS backfill, and capacity analytics. The design required careful compatibility decisions because Archive Tier existed at both the bucket and object level, with customer-visible implications across billing, restore behavior, retention, object operations, and lifecycle policies. The solution covered 3 customer interaction surfaces — Console, CLI, and REST APIs — and 3 object-tier entry points — upload, explicit tier modification, and OLM policy transitions — while separating the MVP customer-facing translation layer from the subsequent metadata backfill.

Result
  • Simplified OCI Object Storage from a three-tier to a two-tier storage model.
  • Impacted 737 paid Archive-tier customers.
  • Addressed an Archive footprint of approximately 419 PB.
  • Reduced long-term engineering, operational, and support complexity associated with maintaining a dedicated Archive tier.
  • Integrated storage capacity metrics with Horizon, improving capacity forecasting and planning.

Seatbelt Execution Output Sweeper
Situation

Seatbelt is a managed service for executing scripts at scale across hosts, providing safety guardrails, velocity control, monitoring, and other execution controls. When customers execute scripts through Seatbelt, script output and error logs are stored in S3; these logs can contain sensitive or critical data from individual hosts and therefore need to be automatically deleted after an appropriate retention period. The goal of this project was to design and implement an automated mechanism to expire and delete Seatbelt execution logs from S3, reducing data-security and compliance risk while giving customers control over log retention.

Action

Drove the project across four workstreams:

  • Defined log-retention requirements: Engaged with recent and frequent customers and EC2 Security Engineers to determine appropriate minimum, maximum, and default values for the Log Expiration Days configuration.
  • Customer-facing configuration: Implemented API and CLI changes to allow customers to configure and update Log Expiration Days.
  • Automated log cleanup: Implemented multithreaded DJS jobs to identify and delete expired execution logs from S3 and maintain the corresponding Log Deletion Time.
  • Production execution: Built the synthesis DJS job using LPT to orchestrate the cleanup workflow at scale.
Complexity

A key design challenge was performing large-scale log cleanup without increasing database load or affecting processes already running on the same fleet.

During design review, I identified that introducing a new indexed Log Expiration Status field could increase database load and negatively impact existing workloads. Instead, I reused an existing indexed status attribute to represent the required state, avoiding the need for an additional database index and reducing the potential impact on fleet performance.

I also initially proposed using a separate DJS job as a backup worker for records whose S3 deletion failed. Based on design feedback, I redesigned the workflow to reuse the same DJS job — first processing newly expired logs, then retrying records that had remained undeleted for more than a day. This eliminated a separate worker, reducing resource and memory consumption while keeping the cleanup and retry logic within a single workflow.

Result

The solution applies to all Seatbelt users and automatically manages expiration for approximately 1,000 script executions per day, covering ~40 GB of execution output daily and 1,200+ GB per month across 30K+ execution logs.

By automatically expiring and deleting execution output from S3, the solution reduces the exposure window for potentially sensitive host data, lowers S3 storage cost, mitigates data-security and compliance risk, and eliminates the need for manual log cleanup.
